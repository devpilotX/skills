# Rewriting an application around evidence

The filter that reads a CV first is looking for evidence, not adjectives, and the human who reads it
second is looking for whether the claims survive a question. This file holds the before-and-after
patterns and the shapes that pass both filters. Every example uses invented figures; the user supplies
their own real numbers, which they must be able to defend out loud.

## The situation, action, result shape

Each bullet states what the situation was, what the user did, and what changed as a result, with the
result carrying a number wherever one honestly exists. The result is the part filters and interviewers
weigh, so it goes at the front or the end where it gets read, never buried in the middle.

Weak: "Responsible for improving system performance."
Strong: "Cut checkout page load from 4.2 seconds to 1.1 by moving image processing off the request path,
which lifted completed purchases on mobile."

The weak version is a job description. The strong version is a claim with a number the user can walk an
interviewer through.

## Replace every adjective about yourself

Adjectives about the candidate are unverifiable and every candidate uses them, so they carry no signal.
Replace each with the fact that would make a reader conclude the adjective on their own.

  "Excellent communicator" becomes running the weekly review across three teams for a year.
  "Detail oriented" becomes owning the reconciliation that closed the month-end without adjustment.
  "Fast learner" becomes shipping in an unfamiliar language within the first month.
  "Team player" becomes covering an on-call rotation through a colleague's leave.
  "Extensive experience" becomes the duration and the scale, such as six years and forty client accounts.

## Mirror the job description, honestly

The first filter is often keyword based and the second is a human who recognises their own words, so use
the vocabulary of the posting where it is true of the user. If the posting says "incident response" and
the user did on-call firefighting, call it incident response. Do not claim a keyword the user cannot back
up in the interview, because the mirror only helps up to the point where it is discovered to be false.

## Structure and length

- One page under ten years of experience, two pages at most beyond that.
- Reverse chronological, most recent first.
- No photograph unless the local hiring convention expects one, since it varies by country and getting it
  wrong is a silent filter.
- Contact details, then a two-line summary only if it says something specific, then experience, then
  education and anything with gate value.
- Cut anything older than fifteen years unless it is the reason the user fits this specific role.

## The cover letter, three short paragraphs

1. Why this employer specifically, meaning something only someone who looked into them would know. Not
   "I admire your mission" but a reference to a product decision, a market they just entered, or a problem
   the role clearly exists to solve.
2. What the user has done that maps to the stated problem, with one piece of evidence, not a restatement
   of the whole CV.
3. What the user wants and a clear close. Short.

If the letter could be sent to another company by changing the name, it says nothing, so rewrite it.

## Interview stories

Write six stories in the situation, action, result shape, each reusable across many questions:

- A conflict, and how it resolved.
- A failure, told honestly, with what changed afterwards.
- A decision made with incomplete information.
- Something taught to someone else.
- Something shipped under real time pressure.
- Something the user was wrong about, and how they found out.

Rehearse the failure story until it is convincing, because an unconvincing failure story reads as worse
than a real admission. For technical roles, practise the answers out loud and against a clock, since the
gap between knowing something and explaining it under time pressure is where most candidates lose.

## What comes out

Delete: objectives that state the obvious, lists of soft skills, technologies used once years ago, and
any claim the user cannot explain in a sentence. Every line left standing is a line the user is ready to
be questioned on.
